{# Packaging guides, shared by the Help page and the upload box on each game's page. #} {% macro zip_steps() %}
  1. Open the folder that holds your game files, so you can see them in the file explorer.
  2. Select everything inside it (Ctrl+A). Don't select the folder itself.
  3. Right-click the selection:
    • Windows 11: Compress to ZIP file
    • Windows 10: Send to → Compressed (zipped) folder
    • Mac: Compress
  4. Give the zip any name. The server renames it.

Selecting the folder itself also works, but then everything sits inside that folder in the zip, and the launch target has to start with the folder's name (for example MyGame/MyGame.exe).

{% endmacro %} {% macro doom_guide(target=none) %}

Put the mod's WAD or PK3 files at the top of the zip. The launcher runs them in GZDoom and installs GZDoom and doom2.wad for players who don't have them.

One file

coolin.zip
└── Coolin.wad

Launch target: Coolin.wad

Several files

coolin16.zip
├── Coolin16.wad
└── intro.pk3

Launch target: leave blank, which loads the whole folder

  • PK3s can be files or unzipped folders; both work.
  • Every update replaces the whole install, so files you remove from the zip disappear for players too.
  • Only fill in IWAD if the mod needs something other than Doom II (e.g. doom.wad). That file has to be in the zip.
{% if target is not none %}{{ current_target(target, 'the whole game folder') }}{% endif %} {% endmacro %} {% macro exe_guide(target=none) %}

Zip the game's whole build folder: the .exe plus every DLL and data folder next to it. The game starts inside the exe's folder, so relative paths work like they do on your PC.

Unity

mygame.zip
├── MyGame.exe
├── MyGame_Data/
├── MonoBleedingEdge/
└── UnityPlayer.dll

Launch target: MyGame.exe

Godot / GameMaker / others

mygame.zip
└── MyGame/
    ├── MyGame.exe
    └── MyGame.pck

Launch target: MyGame/MyGame.exe

  • Test first: copy the build folder somewhere else on your PC and run it from there. If it works, the zip will too.
  • Updates unzip over the old files, so save files in the game folder are kept. Files you remove from the zip stay on players' PCs.
  • Command-line options go in Launch arguments, e.g. -screen-fullscreen 1.
  • Leave out installers, .pdb debug files and *_BurstDebugInformation_DoNotShip folders to keep downloads small.

Put the .jar at the top of the zip, with any lib/ folders or resources it loads next to it.

Let the launcher get Java

blocky.zip
├── game.jar
└── lib/

Launch target: game.jar. Set Java version to what the game needs (8, 17, 21…).

Ship your own Java

blocky.zip
├── game.jar
└── jre/
    └── bin/
        └── javaw.exe

A jre/ folder in the zip is always used first.

  • The jar has to run with java -jar game.jar. If double-clicking it on your PC starts the game, it's fine.
  • Memory options like -Xmx2G go in JVM arguments; options for the game itself go in Launch arguments.
  • Downloaded Java versions are shared between games, so only the first Java game is a bigger download.
{% if target is not none %}{{ current_target(target) }}{% endif %} {% endmacro %} {% macro flash_guide(target=none) %}

Put the .swf at the top of the zip, with any files it loads (other SWFs, XML, music, images) laid out the way the game expects. The launcher plays it in Ruffle, the open-source Flash Player replacement, and installs Ruffle for players automatically.

Single SWF

mygame.zip
└── mygame.swf

Launch target: mygame.swf

SWF that loads other files

mygame.zip
├── mygame.swf
├── levels.xml
└── music/
    └── theme.mp3

Launch target: mygame.swf. Relative paths load from the SWF's folder.

  • Test the SWF in the Ruffle demo first. Older ActionScript 1/2 games work very well; most ActionScript 3 games work, but not all.
  • Useful Launch arguments: --fullscreen, --no-gui (hides Ruffle's menu bar), --width 800 --height 600, and -Pname=value for flashvars.
  • Ruffle keeps save data in its own folder, so updates don't wipe players' progress.
  • Exported as a Flash projector (.exe)? Use the Windows program type instead.
